 Slide 27- 
This slide addresses the freshness problem: How does a cache or browser know if its stored copy is still up to date with the origin server without downloading the whole file again?

The Goal:

Avoid wasting network bandwidth and transmission time re-downloading files that have not changed on the server.

The Mechanism (If-modified-since:):

When a client/cache requests a file it already has stored from an earlier download, it adds a conditional header specifying the timestamp of its stored copy:
If-modified-since: <date>

Scenario A (File Has NOT Changed):

The server checks the file's last modified timestamp on disk. If it hasn't changed since <date>:

The server replies with status code 304 Not Modified.

No file body is sent (saving bandwidth and transmission delay).

The client simply reads and renders its existing local cached copy.

Scenario B (File HAS Changed):

If the file was updated on the server after <date>:

The server replies with standard status code 200 OK and attaches the updated file payload (<data>).

The client replaces its outdated local copy with the new version.


Slide 28- 

This slide explains why HTTP/2 was created by highlighting the major performance bottlenecks in HTTP/1.1.

Primary Objective: Reduce page load delays when fetching multiple web objects over a single connection.

HTTP/1.1 Inefficiencies:

Strict In-Order Responses (FCFS): HTTP/1.1 introduced pipelining (sending multiple requests without waiting for each reply), but the server was forced to return responses in strict First-Come-First-Served (FCFS) order.

Head-of-Line (HoL) Blocking: If the first requested file is a massive video or slow dynamic script, all small files (CSS, icons, HTML) queued behind it are completely blocked until the large transfer finishes.

TCP Packet Loss Stall: If a single TCP packet drops along the way, TCP stops delivery of all subsequent data on that stream until the missing packet is retransmitted.

Slide 29:  HTTP/2 — Server Flexibility and Innovations

This slide details the architectural solutions HTTP/2 (standardized in 2015 via RFC 7540) introduced to solve those limitations.

Backward Compatibility:

Core HTTP semantics remain unchanged: methods (GET, POST), status codes (200, 404), and standard header fields work just as they did in HTTP/1.1.

Key Enhancements:

Priority-Based Scheduling: The client can assign priorities/weights to requested objects (e.g., download critical CSS before low-priority footer images) rather than relying on rigid FCFS ordering.

Server Push: The server can proactively send critical resources (like stylesheets or scripts) to the client’s cache before the client explicitly parses the HTML and asks for them.

Binary Framing & Multiplexing: Instead of sending whole files sequentially, HTTP/2 cuts objects into small, tagged binary frames and interleaves them across the same TCP connection, eliminating application-level Head-of-Line blocking.


Slide 30- 
This slide visually demonstrates how Head-of-Line (HoL) blocking hurts performance in HTTP/1.1.

The Scenario:The client requests four objects back-to-back: one large object ($O_1$, such as a large video file) followed by three tiny objects ($O_2, O_3, O_4$, such as CSS files or small icons).

The HTTP/1.1 Mechanism (Strict FCFS):Because HTTP/1.1 serves responses sequentially in strict First-Come-First-Served order, the server must transmit the entirety of the massive blue object $O_1$ before it can begin sending $O_2$.

The Impact:Even though $O_2, O_3,$ and $O_4$ require very little transmission time, they are forced to wait at the back of the line until $O_1$ finishes completely. This delays critical styling and layout rendering in the browser.

Slide 31-

 HTTP/2: Mitigating HOL Blocking (Interleaved Framing)

This slide shows how HTTP/2 completely eliminates application-layer Head-of-Line blocking.

The Solution (Binary Framing):HTTP/2 slices large and small objects into tiny binary frames.

Interleaved Transmission:Rather than sending all frames of $O_1$ consecutively, the server interleaves the frames of $O_2, O_3,$ and $O_4$ among the frames of $O_1$ over the same single TCP connection.

The Result:The small objects ($O_2, O_3, O_4$) finish transmitting almost immediately because their few frames are slipped in near the front.

$O_1$ is only negligibly delayed, while the browser receives its essential layout files much faster and renders the page without waiting for the large object to finish.

Slide 32
 Transitioning from HTTP/2 to HTTP/3While HTTP/2 fixed Head-of-Line blocking at the application layer, it revealed a deeper problem at the transport layer (TCP), leading to HTTP/3.
 
 The Lingering HTTP/2 Flaw (TCP HoL Blocking):
 
 All HTTP/2 streams share a single TCP connection.
 
 TCP requires bytes to be delivered in strict sequential order. If even a single TCP packet is dropped/lost in transit, TCP halts all data delivery to the application until that missing packet is retransmitted.
 
 Consequently, one lost packet intended for $O_1$ freezes the delivery of $O_2, O_3,$ and $O_4$ as well.
 
 Lack of Native Encryption:Standard TCP connections offer no built-in security unless wrapped in an additional TLS handshake layer.
 
 The HTTP/3 Solution (QUIC over UDP):HTTP/3 moves away from TCP entirely and runs over QUIC (built on top of UDP).
 
 Independent Streams: Packet loss in one object stream does not stall other streams.
 
 Built-in Security: TLS encryption is baked directly into the transport handshake for faster, secure connections.

 Slide 35- 

 What is QUIC?

An application-level transport protocol developed by Google (and later standardized by the IETF) that runs on top of UDP.

Goal: Increase HTTP performance, cut connection latency, and eliminate TCP Head-of-Line blocking.

Real-World Deployment: Deployed at scale across Google services (Chrome browser, YouTube, Google Search servers).

The Traditional Stack Diagram (HTTP/2 over TCP):

Application: HTTP/2 sitting on top of TLS (encryption).

Transport: TCP (manages reliable delivery, ordering, and congestion).

Network: IP (packet routing).

Bottleneck shown: Because TLS and TCP are separate layers, the client must do a TCP handshake first, followed by a separate TLS handshake, adding multiple round-trip delays before application data can flow.


A congestion controller is a built-in traffic management algorithm in transport protocols (like TCP and QUIC) designed to prevent the sender from flooding the network with more data than the intermediate routers and links can handle


Slide 36

This slide outlines how QUIC implements transport-layer reliability and security on top of UDP.

Reusing Proven Mechanics: QUIC adapts battle-tested TCP concepts for error handling, packet loss detection, and congestion control algorithms rather than inventing them from scratch.

Consolidated Connection Setup: Reliability, congestion parameters, cryptographic state, and authentication are all established simultaneously in one single round trip ($1\text{ RTT}$) or even $0\text{ RTT}$ on return visits.

Stream-Based Multiplexing: Multiple application streams share one underlying QUIC connection:

Each stream gets independent reliable delivery (so errors stay isolated).

All streams share a common congestion controller across the connection.

Slide 37: QUIC Connection Establishment ($2\text{ RTT}$ vs. $1\text{ RTT}$)

This slide visually compares the connection startup time of standard HTTPS/TCP versus QUIC.

Traditional TCP + TLS (Left Side):Handshake 1: The client performs a standard TCP 3-way handshake to establish transport reliability and congestion tracking ($1\text{ RTT}$).

Handshake 2: After TCP connects, the client initiates the TLS handshake to negotiate cryptographic keys and authenticate certificates ($1\text{ RTT}

$).Total Penalty: $2\text{ serial handshakes}$ ($2\text{ RTTs}$) pass before any application data can be sent.

QUIC Handshake (Right Side):QUIC combines transport setup and cryptographic key exchange into a single combined handshake.

Total Penalty: Only $1\text{ RTT}$ to establish reliability, congestion state, and TLS 1.3 encryption, allowing application data to travel right alongside the first flight.

Slide 38:

 Streams, Parallelism, and Head-of-Line Blocking (HTTP/2 Limitation)

This slide provides the architectural breakdown showing why HTTP/2 suffers from transport-level stalls.

Layer Separation in HTTP/2:At the Application Layer, multiple HTTP requests are multiplexed and encrypted into streams via TLS.

At the Transport Layer, everything passes through a single monolithic TCP Reliable Data Transfer (RDT) and Congestion Control pipeline.

The Fatal Flaw (Red "error" on diagram):Because TCP manages reliability for the stream as a whole, a packet transmission error in one stream halts the entire TCP RDT pipe.

The transport layer refuses to pass any received bytes up to TLS and the application, causing every independent HTTP request to stall until the dropped packet is retransmitted.
